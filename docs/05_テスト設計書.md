# テスト設計書

## 1. はじめに
本書はtms-appのテスト方針・テスト構成を記述する。バックエンド（Laravel/Pest）・フロントエンド（Angular/Vitest）それぞれのテスト戦略と、CI（`.github/workflows/ci.yml`）との連携をまとめる。

## 2. テスト方針の全体像

| 層 | フレームワーク | 種別 | カバレッジ方針 |
|---|---|---|---|
| バックエンド | Pest 4（PHPUnit 12基盤） | Unit（Model/Policy/Action/Enum/Exception単位）＋Feature（APIエンドポイントをSanctum認証込みでE2E的に検証） | **行カバレッジ100%を必須**（`php artisan test --coverage --min=100`。未達はCI失敗） |
| バックエンド（静的解析） | Laravel Pint | コードスタイル検査 | `vendor/bin/pint --test`をCIで必須実行 |
| フロントエンド | Vitest（`@angular/build:unit-test`、jsdom環境） | Unit（Service/Guard/Interceptor/Util/共有コンポーネント）＋Component（Feature単位、依存はモック） | 数値目標のカバレッジ%は設定していないが、**モデル定義を除く全.tsファイルに対応するspecファイルを用意する**方針（2026年9月時点で100%達成、後述） |
| インフラ/CI定義 | actionlint | GitHub Actionsワークフローの構文・意味検証 | ローカルで`actionlint`実行（CIには未組み込み、今後の課題） |

いずれのテストも「意図の伝わるテスト」（CLAUDE.md）を徹底し、テスト名を日本語の仕様文として書く（例:「上司による代理申請は、申請元の上司自身も承認できず、人事の承認が必要になる」）。

## 3. バックエンドテスト設計

### 3.1 ディレクトリ構成と対象
```
tests/
├── Unit/
│   ├── Models/       … Eloquentモデルのリレーション・スコープ・ビジネスロジックメソッド
│   ├── Policies/     … 認可ロジック（ロール・関係性ごとの許可/拒否）
│   ├── Actions/       … Actionクラス単体（DBに実際に書き込み、結果を検証）
│   ├── Console/Commands/ … バッチコマンドの起動確認
│   └── Requests/     … 存在する場合、FormRequestの個別ルール
└── Feature/
    ├── Employees/     … 部署・役職・従業員・異動・委任のAPIエンドポイント
    └── Trainings/     … 研修カタログ・レッスン・受講登録・申請承認のAPIエンドポイント
```

80ファイル・464テスト・926アサーション（2026年9月時点、予算・コスト管理／研修効果測定（ROI）／監査ログ実装後）。

### 3.2 テストデータの作法
- **Factory**: 全モデルに`database/factories/`のFactoryを用意。状態別のバリエーションは`->hr()`（Employee）、`->approved()`/`->rejected()`/`->cancelled()`/`->multistage(n)`（TrainingRequest）のようなnamed stateで表現する。
- **ヘルパー関数**: `tests/Pest.php`の`createEmployeeWithAssignment($employeeAttributes, $assignmentAttributes)`で「配属済みの従業員」を1行で用意する（部署・役職はFactory任せ、`manager_id`等だけ明示することが多い）。
- **日付に依存するテスト**: `Carbon::setTestNow()`で「今日」を固定し、年度またぎ等の分岐（例: `Employee::hiredInCurrentFiscalYear()`の1〜3月ケース）を決定的にテストする（`afterEach`で必ずリセット）。
- **ファイルアップロード**: `Illuminate\Http\UploadedFile::fake()->create(...)`、ストレージ検証は`Storage::fake('public')`＋`assertExists`/`assertMissing`。
- **通知**: `Notification::fake()`＋`assertSentTo`で送信先・文面を検証（実メール送信はしない）。
- **監査ログObserver**: `updated`イベントで「タイムスタンプのみの変化は記録しない」分岐を確実に踏ませるため、`touch()`ではなく`forceFill(['updated_at' => now()->addMinute()])->save()`で明示的に差分を作る（同一秒内の`touch()`は保存自体がスキップされ得るため）。

### 3.3 カバレッジ運用
- `php artisan test --coverage --min=100`をローカル・CI双方で実行。カバレッジドライバはローカル（Sail）はXdebug、CIはpcov（`shivammathur/setup-php`の`coverage: pcov`指定、高速なため）。
- 100%未達の典型例と対処: 条件分岐の片側だけテストしている（例: 年度またぎの`else`分岐）→ `Carbon::setTestNow()`で該当条件を明示的に再現するテストを追加する。

### 3.4 Feature testの認可検証パターン
権限まわりの機能はほぼ全て、以下の組み合わせをFeature test側でも確認する（Unitでの`Policy`単体テストと二重に担保する）。
- 人事は無条件に許可される（`Gate::before`）
- 対象ロール（本人・上司・部下を持つ管理職等）は許可される
- 無関係な第三者・従業員レコードの無いユーザーは403になる
- 状態違反（例: 承認待ちでない申請への操作）は422になる

## 4. フロントエンドテスト設計

### 4.1 テスト基盤
- ビルダー: `@angular/build:unit-test`（Vitest + jsdom、Karmaは使用していない）。
- 実行: `npm test`（`ng test`）。ウォッチモードではなく1回実行して終了するため、CIでもそのまま実行できる。
- HTTPのモック: `provideHttpClientTesting()` + `HttpTestingController`で実際のHTTPリクエスト（メソッド・URL・ボディ）を検証する（Serviceのテストのみ。Componentのテストでは各Serviceそのものをモックする）。
- DIのモック: `TestBed.configureTestingModule({ providers: [{ provide: XxxService, useValue: {...} }] })`で、Component1つに対して必要なメソッドだけを`vi.fn()`で個別にスタブする。
- ルーティングが絡む箇所: `provideRouter([])`を使い、実際のナビゲーション結果ではなく「`Router.navigate`/`navigateByUrl`が正しい引数で呼ばれたか」をスパイで検証する（存在しないルートへの遷移で発生する非同期エラーを避けるため、副作用を伴うnavigateは`mockResolvedValue(true)`でスタブ化する）。
- 関数型Guard/Interceptorのテスト: `TestBed.runInInjectionContext(() => guardFn(...))`で`inject()`を使う関数を直接呼び出す。

### 4.2 テスト対象と方針（2026年9月時点で全ファイル対応）

| 分類 | 対象 | 方針 |
|---|---|---|
| Service（10件） | Auth/Employee/MasterData/Report/TrainingEnrollment/TrainingRequest/Training/DepartmentBudget/TrainingFeedback/AuditLog | 全メソッドについて、呼び出しHTTPメソッド・URL・リクエストボディが仕様通りであることを検証（テーブル駆動）。`AuthService`は状態変化（`isAuthenticated`/`isHr`等のsignal）も検証 |
| Guard（2件） | authGuard / hrGuard | 認証済み/未認証、人事/非人事の分岐と、リダイレクト先UrlTreeを検証 |
| Interceptor（1件） | credentialsInterceptor | withCredentials付与、XSRFヘッダーの付与条件（GET等では付与しない、Cookie無ければ付与しない、既存ヘッダーは上書きしない） |
| Util（4件） | csv / forms / kana / fiscal-year | 純粋関数のため入出力を網羅的に検証。`downloadCsv`はDOM API（`URL.createObjectURL`等）をスパイして副作用を検証 |
| 共有コンポーネント（3件） | status-label / progress-bar / bar-chart | ラベル変換の網羅、`input.required`の反映、0除算等の境界値 |
| 機能コンポーネント（18件） | 全Feature配下＋layout/shell | 「サービス呼び出しの引数」「成功/失敗時のsignal状態遷移」「フォームバリデーションによるガード」を中心に検証（詳細は4.3） |

ファイル単位のspec対応表（モデル定義ファイルを除く）は、`find src/app -name "*.ts" -not -name "*.spec.ts" -not -path "*/models/*"`の結果と1:1で対応している（漏れが出ないよう、新規ファイル追加時はこのルールを維持する）。

## 5. CIとの連携

`.github/workflows/ci.yml`（push/PR時に自動実行、詳細はインフラのREADME・ワークフローファイル参照）:

| ジョブ | 内容 |
|---|---|
| backend | Postgres 18サービスコンテナ起動 → `composer install` → `.env`準備・`key:generate` → `migrate --force` → `php artisan test --coverage --min=100` → `vendor/bin/pint --test` |
| frontend | `npm ci` → `npm run build -- --configuration production` → `npm test` |

いずれか1つでも失敗するとCI全体が失敗する。ローカルでは`sail artisan test --coverage --min=100`（バックエンド）・`npx ng test`（フロントエンド）で同等の検証ができる。

## 6. 手動検証（E2E相当）の方針
自動テストではカバーしにくい「実際のDB・実際のブラウザ相当の挙動」は、新機能追加のたびに以下の手順で手動検証している（本書の対象外だが、開発フローの一部として記録）。
- `tinker`で使い捨てデータ（部署・従業員・研修等）を作成
- Sanctumのセッション認証をcurlで再現（`/sanctum/csrf-cookie`→ログイン→対象APIを呼ぶ）し、正常系・異常系（422/403）を確認
- フロントエンドは`ng build`で本番相当ビルドが通ることを確認し、必要に応じて開発サーバー（`ng serve`）上で実際の画面操作を確認
- 検証後は作成した使い捨てデータを`tinker`で削除し、実データに影響を残さない
