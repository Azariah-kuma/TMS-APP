## 2. システム概要

### 2.1 システムの目的
従業員の研修受講・進捗管理を一元化し、以下を実現する。

- 研修カタログの管理（研修・レッスン単位の教材登録）
- 従業員への研修の割り当て（人事による直接割当／部署一括／全社一括）
- 従業員自身または上司による研修受講の「申請」と、上司・人事による「承認／却下」
- 受講進捗の記録（レッスン単位の完了チェック、または研修全体の進捗率）
- 部署・役職・上司関係（異動履歴）を含む組織情報の管理
- 人事向けの受講状況レポート（画面表示・CSV出力）

### 2.2 対象ユーザーとロール
本システムのユーザーは全員「従業員（Employee）」として登録され、以下の2つの正式ロールを持つ。

| ロール（`employees.role`） | 説明 |
|---|---|
| `employee`（一般社員） | 自分自身の研修状況の閲覧・申請が可能。部下を持つ場合は上司として振る舞う（後述） |
| `hr`（人事） | 全ての機能・全データに対する管理権限を持つ（詳細は「4. 権限モデル」参照） |

**「上司（管理職）」はロールではなく、組織構造から動的に導出される relational な概念**である。`employee_assignments.manager_id` の連鎖により「誰が誰の上司か」が決まり、一般社員ロールのままでも部下を持てば「上司」として振る舞える（部下の研修状況閲覧・代理申請・承認など）。

### 2.3 システム構成

```
┌─────────────────────────┐        HTTPS / JSON        ┌──────────────────────────────┐
│  Angular 22 SPA (frontend)│ ───────────────────────── │  Laravel 13 API (backend)     │
│  - Standalone Components  │   Cookie(Sanctum SPA)      │  - Controller / Action / Policy│
│  - Signals / Reactive Form│   + XSRF-TOKEN header      │  - FormRequest / Exception     │
└─────────────────────────┘                             └───────────────┬───────────────┘
                                                                          │
                                                          ┌───────────────┼───────────────┐
                                                          │               │               │
                                                   PostgreSQL      Queue(database)     Mail(SMTP)
                                                  （業務データ）    （通知の非同期送信）  （招待/リマインド）
```

- **バックエンド**: Laravel 13（PHP）、認証は Laravel Sanctum の SPA（Cookieベース・ステートフル）モード
- **フロントエンド**: Angular 22（スタンドアロンコンポーネント、Signalsによる状態管理、Reactive Forms、`@if`/`@for`制御構文）
- **DB**: PostgreSQL（部分UNIQUEインデックスやCHECK制約などPostgreSQL固有機能を利用）
- **キュー**: `QUEUE_CONNECTION=database` による非同期通知送信（研修割当・期限リマインド・期限超過通知）
- **開発環境**: Laravel Sail（Docker）

### 2.4 技術的な設計方針
- **Fat Controllerの禁止**: Controllerはリクエスト受領とレスポンス返却に専念し、業務ロジックは `app/Actions/` 配下のActionクラスに委譲する。
- **FormRequestによるバリデーション徹底**: 入力検証はすべて独立したFormRequestクラスで行う。
- **ドメイン例外の統一設計**: 業務ルール違反はすべて `UnprocessableDomainException` を継承した専用例外として表現し、一律 HTTP 422 で返却する（詳細は詳細設計書 4章）。
- **排他制御**: 同時実行による不整合が起こりうる処理（役職の序列挿入、異動登録、研修申請の承認/却下/取消）では `lockForUpdate()` を用いた行ロック＋トランザクションで整合性を担保する。

## 4. 権限モデル

### 4.1 「人事は全権限」の原則（Gate::before）
`app/Providers/AppServiceProvider.php` に定義された `Gate::before` フックにより、ログインユーザーが人事ロール（`employee.role === 'hr'`）である場合、**すべての認可チェック（Policy／Gate）が無条件で許可**される。

```php
Gate::before(fn (User $user, string $ability) =>
    $user->employee?->isHr() ? true : null
);
```

このため、各Policyクラスの管理系メソッド（`create`/`update`/`delete`等）は「人事以外は不可」を表現するために単純に `false` を返す実装になっているものが多い。人事の許可は個別のPolicyロジックではなく、常にこの共通フックが担う。

レポート閲覧権限（`viewReports` Gate）は明示的に `false` 固定で定義されており、Policyクラスすら持たない。人事のみが `Gate::before` 経由でアクセスできる。

### 4.2 「上司」の判定ロジック
- `employee_assignments.manager_id` により、従業員ごとに現在の上司が1件（`ended_at IS NULL`）決まる。
- `Employee::hierarchySubordinateIds()`: `manager_id` の連鎖をBFSで辿り、直属・間接を問わず組織階層上の部下ID一覧を返す（純粋な組織構造のみ、委任は含まない）。
- `Employee::subordinateIds()`: 上記の階層部下に、有効な委任（後述）で受け取った部下を合流させたID一覧を返す。多くの認可判定・データ絞り込み（`visibleTo`スコープ等）はこちらを使用する。
- `Employee::isManagerOf()`: 対象が `subordinateIds()` に含まれるかで判定。

### 4.3 委任（Delegation）
人事のみが登録・取消できる、上司権限の期間限定委任機能。委任元（`delegator`）の**直属・間接の部下**が、委任先（`delegate`）の `subordinateIds()` に一時的に加算される。委任は一段のみ有効で、委任の委任（多段）はサポートしない。同一の委任元・委任先の組み合わせで期間が重複する委任は作成できない。

### 4.4 権限の代表的な非対称ルール
- **研修申請の承認**: 従業員本人が申請した（自己申請）ものに限り、その上司が承認・却下できる。**上司が部下の代わりに代理申請したものは、その上司自身も含め、いかなる上司も承認できない**（人事のみが決裁可能）。これは「代理申請の時点で受講させる意思決定は済んでいる」という業務上の理由による。
- **受講進捗の更新**: 上司であっても部下の進捗を直接更新することはできない（閲覧のみ）。進捗更新は本人または人事に限定される。
- **役職・部署の削除**: 配属履歴（`employee_assignments`）で使用中の役職・部署、および研修の閲覧対象部署として使用中の部署は、DBの参照整合性を保つため削除できない（誤操作防止のUI設計と対をなす）。

### 4.5 研修カタログの閲覧制限（対象者の限定）
研修は既定では全従業員に公開されるが、以下の条件を個別またはOR条件で組み合わせて閲覧対象を限定できる（人事が研修登録時に設定）。

| 条件 | 説明 |
|---|---|
| 対象部署 | 指定した部署に現在所属する従業員のみ閲覧可 |
| 管理職のみ | 現在1人以上の直属部下を持つ従業員（管理職）のみ閲覧可 |
| 新入社員のみ | 入社日が今年度（4/1〜翌3/31）に含まれる従業員のみ閲覧可。年度が変わると自動的に対象から外れる |

いずれも設定していなければ「全員」に公開される。人事は`Gate::before`により、対象者の設定に関わらず常に全ての研修を閲覧・管理できる。

### 4.6 多段階承認（重要研修向け）
高額・重要な研修は、人事が「多段階承認が必要」フラグと必要な承認段階数（例: 2段階）を設定できる。この設定がある研修は次の2点で通常の研修と異なる。

- **閲覧**: 対象者の設定に関わらず、承認者になり得る**管理職には常に表示される**（事前に把握できるようにするため）。人事も従来通り把握できる。
- **承認フロー**: 従業員本人による自己申請のみが対象（上司による代理申請は従来通り人事のみが決裁）。1段階目は申請対象本人の直属の上司が決裁し、2段階目以降は「直前の段階を決裁した人の、さらに上司」が決裁する（部長→役員のように、承認のたびに1つ上の階層へ進む）。全段階の承認が揃って初めて申請が確定し、受講登録が作成される。途中の段階で却下されれば、残りの段階を待たず即座に却下が確定する。

### 5.1 共通UI設計方針
- 角丸・影・グラデーションを排した実用本位のデザイン（`.panel`/`.table`/`.badge`等の共通クラス）。
- フォームエラーは `.field-error`（項目ごと）、サーバーエラー全体は `.alert` で統一表示。
- 破壊的操作（削除等）は、誤操作防止のため既定で折りたたんでおき、明示的なトグル操作後にのみボタンを表示する（役職一覧画面の「操作」ボタン等）。

## 6. 通知・外部連携

| 通知 | トリガー | 送信方式 |
|---|---|---|
| 初回パスワード設定案内 | 従業員オンボード登録時、または招待再送信操作時 | 同期送信（`SetInitialPasswordNotification`） |
| 研修割当通知 | 研修への受講登録（直接／一括／申請承認経由）時 | キュー経由（`TrainingEnrollmentCreatedNotification`） |
| 受講期限前日リマインド | 日次バッチ（毎日9:00起動） | キュー経由（`TrainingDueReminderNotification`） |
| 受講期限超過通知 | 日次バッチ（毎日9:00起動）、期限翌日に本人・上司・全人事へ通知 | キュー経由（`TrainingOverdueNotification`） |

CSVエクスポート（受講状況）・CSVインポート（従業員一括登録）はいずれもCSVインジェクション対策（`=`/`+`/`-`/`@`で始まるセル値の先頭にシングルクォートを付与）を実施している。

## 7. 対象外・今後の課題

プロジェクトレビューで指摘された以下の観点のうち、多段階承認（4.6参照）は対応済み。残りは未着手。

- 研修申請の却下後の再申請導線（差し戻し→修正→再提出を1つの業務フローとして繋ぐ機能。現状は却下後、改めて新規に申請し直す形になる）
- 研修の効果測定（テスト結果・理解度・受講後アンケート）の仕組み
- 研修の予算・コスト管理（研修費用の記録、予算超過アラート）
- 研修削除時の使用中データとの整合性チェック（受講記録・申請が存在する研修の削除に対する参照整合性チェックは未実装）
- 多要素認証、パスワードポリシーの強化
